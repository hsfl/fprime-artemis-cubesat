# F Prime Testing

Platforms: everything here runs natively on macOS and Linux; Windows users run
it inside WSL2 (per the Student Platform Policy). No hardware, no `sudo`.

## Run Tests (this repo)

Full laptop regression (Python tests + build + component UTs + automated demo):

```bash
cd <repo-root>
./tools/validate_local.sh            # everything
./tools/validate_local.sh --skip-demo    # skip the automated demo sequence
```

Component UTs only (from `ArtemisRpiTeensy_N2`, venv active):

```bash
fprime-util generate --ut -f
fprime-util build --ut
fprime-util check --all
```

Single component: run `fprime-util check` from inside that component's
directory (e.g. `Components/MissionApp/`).

Note: `settings.ini` sets `FPRIME_ENABLE_FRAMEWORK_UTS=OFF` — framework
(lib/fprime) UTs are intentionally excluded; only project component UTs build.
Do not "fix" a missing framework test target by flipping that flag.

## Adding a UT to a Component

1. Layout:

   ```text
   Components/MyThing/test/ut/MyThingTester.hpp
   Components/MyThing/test/ut/MyThingTester.cpp
   Components/MyThing/test/ut/MyThingTestMain.cpp
   ```

   (`fprime-util impl --ut` from the component dir generates starter stubs.)

2. Append to the component's `CMakeLists.txt` (matches repo style):

   ```cmake
   set(UT_SOURCE_FILES
       "${CMAKE_CURRENT_LIST_DIR}/MyThing.fpp"
       "${CMAKE_CURRENT_LIST_DIR}/test/ut/MyThingTestMain.cpp"
       "${CMAKE_CURRENT_LIST_DIR}/test/ut/MyThingTester.cpp"
   )
   set(UT_MOD_DEPS
       Components_Types
       STest
   )
   set(UT_AUTO_HELPERS ON)
   register_fprime_ut()
   ```

   `UT_AUTO_HELPERS ON` autogenerates the `TesterHelpers` (port connection)
   code so you don't maintain it by hand.

3. Tester class extends the generated GTest base:

   ```cpp
   MyThingTester::MyThingTester()
       : MyThingGTestBase("MyThingTester", MAX_HISTORY_SIZE),
         component("MyThing") {
       this->initComponents();
       this->connectPorts();
   }
   ```

4. `TestMain.cpp` holds plain `TEST(...)` cases that instantiate the tester
   and call its test methods.

## Tester Idioms (autogenerated helpers)

| Do | Helper |
|----|--------|
| Invoke an input port | `this->invoke_to_<portName>(portNum, args...)` |
| Send a command | `this->sendCmd_<MNEMONIC>(instance, cmdSeq, args...)` |
| **Drain the queue (active components)** | `this->component.doDispatch()` — async commands/ports do NOTHING until dispatched |
| Assert event emitted | `ASSERT_EVENTS_<Name>_SIZE(n)`, `ASSERT_EVENTS_<Name>(index, args...)` |
| Assert telemetry written | `ASSERT_TLM_<Chan>_SIZE(n)`, `ASSERT_TLM_<Chan>(index, value)` |
| Assert output port called | `ASSERT_from_<portName>_SIZE(n)`, `ASSERT_from_<portName>(index, args...)` |
| Assert command response | `ASSERT_CMD_RESPONSE_SIZE(n)`, `ASSERT_CMD_RESPONSE(index, opcode, seq, response)` |
| Reset histories between phases | `this->clearHistory()` |

Rate-driven logic: tick it explicitly in a loop —
`for (U32 t = 0; t < 30; ++t) this->invoke_to_run(0, 0);`

See `Components/MissionApp/test/ut/MissionAppTester.cpp` for a full
worked example (command → dispatch → event/telemetry/port assertions).

## Common UT Pitfalls

- Sent an async command but forgot `doDispatch()` → all assertions see empty
  histories.
- Assertion index is per-history (0-based, in emission order), not per-tick.
- Forgot `clearHistory()` between test phases → counts off by earlier events.
- UT build uses a separate cache: after `.fpp` changes rerun
  `fprime-util generate --ut -f`.
- New UT not discovered → `register_fprime_ut()` missing or `UT_SOURCE_FILES`
  doesn't include the component `.fpp`.

## What to Test (repo priority)

Demo-first rule applies to tests too: cover the demo-story behaviors —
mode transitions, scheduled collection, storage/downlink handoff events —
before edge-case polish. Placeholder/request-state commands should be tested
for the events they emit, not for hardware effects they don't have.

## Integration Testing (GDS Test API)

For end-to-end command/telemetry tests against a running deployment, use the
GDS integration test API (pytest-based):
`ArtemisRpiTeensy_N2/lib/fprime/docs/user-manual/gds/gds-test-api-guide.md`.
The Python-side transport/receiver tests live under
`ArtemisRpiTeensy_N2/tools/tests/` and run inside `validate_local.sh`.
