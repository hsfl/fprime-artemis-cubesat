01 · The six ideas to memorize

Mental models before details

If these six models are clear, the codebase stops looking like unrelated C++, Python, Arduino, and web folders. It becomes one distributed pipeline with explicit ownership boundaries.

DS

A distributed system on a bench

There is no single “app.” The laptop, two Teensys, Raspberry Pi, two radios, and camera cooperate across process and hardware boundaries.

2P

Two planes, two jobs

Control plane: commands/events/telemetry through CCSDS. Data plane: bulk science through a separate packet-and-file protocol.

API

FPP is the contract

Component `.fpp` files declare typed ports and ground interfaces. Generated C++ and the dictionary make those contracts executable and visible in GDS.

HAL

Policy → contract → mechanism

Applications decide why/when. Managers define a stable subsystem capability. Drivers implement the camera, radio, PDU, or simulator details.

MUX

One wire, several virtual lanes

The Pi has one UART to the satellite Teensy, so `UartChannelMux` labels traffic. Channel numbers are logical lanes, not extra physical wires.

✓

“Sent” is not “received”

A flight-side completion event proves the sender finished. Ground CRC + decode proves every required byte arrived and still has meaning.

Scope truth: this page explains the current C3M demo on the active `epscorc3m` transport identity. It is a demo/HIL architecture, not a flight-readiness, encryption, authentication, or full spacecraft qualification claim.
Numbering warning: RF logical channels, Pi↔satellite-Teensy UART virtual channels, and ground USB interface numbers are related mappings—not one shared numbering system. Always name both the boundary and the number.

04 · F´ without the jargon wall

The framework fundamentals

F´ supplies the Pi architecture and code generation. It turns explicit contracts into one component graph. It also generates the ground dictionary.

Component

A module with private state and a public interface. Active components own a thread + queue; passive components run in the caller’s context.

Port

A typed connection between components. Sync is a direct call, async is queued, guarded is a mutex-protected direct call.

Topology

The compile-time wiring graph: which component instances exist, which ports connect, and which rate group ticks each component.

Dictionary

The ground schema generated from FPP: command opcodes/arguments, events, telemetry, parameters, and Data Product definitions. It must match the exact deployed Pi build.

Command

A one-shot request from ground. The handler must validate, act, and return a command response so GDS knows completion status.

Event

A timestamped statement that something happened: mode changed, capture completed, downlink failed. It is history, not current state.

Telemetry

A sampled current value: mode, pending seconds, packet counts, radio state. Use it to monitor and chart state over time.

Parameter

A tunable setting. Setting changes runtime state; saving through the parameter database is what makes it persist.

Runtime model: Main.cpp starts the Linux deployment. A UART read thread feeds UartChannelMux. Active components own queues and threads. Passive components run in the caller’s context. The Linux timer drives rate groups at 1 Hz, 0.5 Hz, and 0.25 Hz. A blocking handler can stop other work in the same execution context.
Source versus generated output: component .fpp files and topology files are source contracts. Generation creates C++ support and the GDS dictionary. config/transport_constants.json is the transport source. LinkCfg.hpp and the two Teensy link_protocol.hpp files are generated outputs. Change the source first. Then regenerate, rebuild each affected target, and deploy the matching artifacts.

Application → Manager → Driver

APPLICATION · MISSION POLICYWhy and when?

MissionApp, ScienceApp, CommsApp, SoHApp. They coordinate the story and should not know camera APIs, UART frames, or PDU bytes.

MANAGER · STABLE CAPABILITYWhat capability?

PayloadManager, StorageManager, EpsManager. They expose mission-facing behavior that stays stable when hardware changes.

DRIVER · MECHANISM / HALHow on this hardware?

PayloadDriver_Lepton, PayloadDriver_Boson, EpsDriver_Artemis. Protocol and hardware glue belongs here.

Camera selector seam: the current payload path adds PayloadDriverSelector between the manager and the Lepton/Boson drivers. It routes one capture to the selected driver without forking mission logic.

Trace one command: SCHEDULE_COLLECTION(10)

Ground laptop

Dictionary turns a name into wire data

GDS uses the matching dictionary to find the command opcode. GDS serializes the U32 argument into a CCSDS telecommand.

USB + RF + UART

Bridges preserve bytes, not meaning

Ground USB interface 0 → ground Teensy → RF segments → satellite Teensy → UART channel 0. These layers do not know the command meaning.

Pi transport + C&DH

The Pi unwraps and dispatches

UartChannelMux removes the D4 C3 wrapper. ComCcsds removes the CCSDS frame. CdhCore.cmdDisp sends the opcode to missionApp.

MissionApp queue

The active component handles it

The asynchronous command waits in the MissionApp queue. The handler validates the delay and sets the pending state. It emits CollectionScheduled and acknowledges the command.

1 Hz rate group

The scheduler advances the story

Each 1 Hz run tick decreases the pending delay. At zero, a typed port call starts the science pipeline. The process does not sleep for ten seconds.

Reverse control path

Evidence returns to the ground

Command responses, events, and telemetry return through CdhCore → ComCcsds → UART channel 0 → RF → GDS.

Science lifecycle: camera to decoded artifact

Selected driver captures

Lepton uses its camera backend; Boson uses its own. The driver validates the frame and serializes the correct record schema.

F´ Data Products writes the `.fdp`

The driver does not announce success until the Data Product writer reports completion. That prevents a descriptor from pointing at a half-written file.

A typed descriptor moves, not raw pixels

Product ID, bytes, source kind, Pi path, and CRC move through ScienceApp → StorageManager → CommsApp.

The app retains the latest descriptor

The operator can request a completed picture again with a new transfer ID. A new capture replaces the descriptor. A Pi or F´ restart clears it.

Pi uploads to the satellite Teensy cache

PayloadDownlinkApp uses channel 2 target 3: begin, 200-byte chunks, commit-and-send. The cache bounds memory and decouples Pi scheduling from RF pacing.

The satellite emits channel-1 science packets

Header records identify transfer/product/size/count/CRC. Indexed data records carry 35 bytes. The end record closes nominal transmit.

The ground owns end-to-end completion

The receiver tracks indexes, requests missing packets, verifies the complete `.fdp` CRC, then calls the matching decoder using the dictionary/Data Product identity.

07 · Find the first broken boundary

Debug by ownership, not guesses

Start at the visible symptom, move one boundary at a time, and ask what evidence the owning layer should produce. Counters and identities beat broad “radio is broken” conclusions.

GDS page loads, but commands do not reach the Pi
  1. Confirm that GDS uses ground USB interface 0.
  2. Confirm that GDS uses the dictionary from the deployed Pi build.
  3. Check the ground uart_rx and rf_tx_pkt counters.
  4. If local emulation used the global F´ IPC endpoints, restart the complete hardware GDS process tree.

A browser refresh does not restart the backend.

The schedule command succeeds, but no new ScienceStored appears
  1. Follow CollectionScheduled → CollectionTriggered → PayloadRequestRouted → capture events → ScienceProductReady → ScienceStored.
  2. Find the first missing event.
  3. Inspect the component that owns that event.
  4. Check the selected driver and camera before you inspect RF.

The Pi captures the frame before downlink starts.

PayloadDownlinkStarted appears, but the receiver sees nothing
  1. Confirm that the receiver was ready before the request.
  2. Confirm that the receiver owns ground USB interface 2.
  3. Inspect satellite cache target-3 responses.
  4. Inspect satellite payload, RF channel-1, and ground payload counters.
  5. Inspect serial ownership last.

Flight-side completion does not prove laptop delivery.

The receiver saves a partial image or shows white pixels

In science products, white or NaN regions identify unavailable packet bytes. The receiver preserves each pixel position.

In preview images, white pixels are expected loss markers. Preview does not repair missing data.

Identify the applicable contract before you report a defect.

CRC fails even though packet counts look close
  1. Check for missing packet indexes.
  2. Check the transfer ID and product ID.
  3. Check the final packet length.
  4. Check the dictionary and Data Product format.
  5. Check the whole-file CRC.

Do not use a CRC-failed full product as authoritative science. Keep the file as a partial artifact.

Preview pauses for several seconds

Preview is response-paced and keeps only the newest frame. One lost local RPC response abandons the current frame after five 1 Hz ticks.

The app then requests a new frame. This behavior can cause a visible gap of approximately 7–8 seconds.

Channel 0 becomes noisy or PING misses during science downlink

The RFM23BP is half-duplex and has limited capacity.

  1. During the timed demo, send only one proof PING.
  2. Keep other GDS traffic quiet.
  3. If the response is missing, retry once when the link is idle.
  4. Record the directional counters.
  5. Do not send many duplicate commands.
Which “channel 2” do people mean?

Satellite UART channel 2 carries local RPC between the Pi and satellite Teensy. It does not cross RF.

Ground USB interface 2 carries RF channel-1 payload traffic to the receiver. The two number systems are different.

09 · From zero context to useful changes

New-developer path

You do not need to memorize every component. Learn to trace one command and one artifact across system boundaries. Change only the layer that owns the behavior.

Before you touch anything: establish a safe local baseline. 
cd ~/Developer/fprime-artemis-cubesat
git status --short --branch
git submodule status --recursive
. ArtemisRpiTeensy_N2/fprime-venv/bin/activate
./tools/validate_local.sh --demo c3m

The safe path uses local emulation and replay data. It does not use a Pi, Teensy, radio, or live camera.

A pass has these results:

  • The script exits with status 0.
  • Generated-constant checks, F´ builds, and tests pass.
  • Three cycles produce three separate ground .fdp files.
  • Each file decodes to 160×120 pixels.
  • The script prints the final three-cycle PASS message.

This result is software evidence only. Use the proof ladder before you make a HIL claim.

First 90 minutes

  1. Read this page once without opening code.
  2. Open topology.fpp and find MissionFlow, ManagerDriverBindings, and Communications.
  3. Open MissionApp.fpp; identify commands, ports, events, and telemetry.
  4. Trace SCHEDULE_COLLECTION into its C++ handler and rate-group tick.
  5. Trace ScienceProductDescriptor through storage and comms.
  6. Run the local validation command above and inspect its run-log artifacts before touching hardware.

10 · Vocabulary decoder

Searchable glossary

Use the repo’s full glossary for depth. This compact set covers the terms needed to read the demo code and runbooks without prior spacecraft context.

F´ / F Prime
NASA/JPL component-based flight-software framework running on the Pi.
FPP
F Prime Prime language used to declare component interfaces, types, instances, and topology wiring.
Component
Encapsulated module with typed ports and optional ground interfaces.
Port
Typed component-to-component invocation edge. Not a USB or TCP port.
Topology
The graph of component instances and port connections that becomes the deployment.
Deployment
The complete F´ executable and generated support artifacts for one system configuration.
Dictionary
Ground-readable schema for commands, events, telemetry, parameters, types, and Data Products.
GDS
F´ Ground Data System: current command, event, and telemetry web surface.
C&DH
Command and Data Handling: dispatch, event/telemetry collection, framing, and related flight services.
CCSDS
Space-data framing/packet standards used on the GDS-facing control plane.
TC / TM
Telecommand goes ground→spacecraft; telemetry transfer frame goes spacecraft→ground.
APID
Application Process Identifier inside CCSDS packets; sequence warnings expose dropped packet history.
SOH
State of health: normalized subsystem health and basic operating status.
OBC
On-Board Computer. Here it is a split Pi + Teensy prototype system.
HAL
Hardware Abstraction Layer; drivers isolate mission logic from a specific camera, PDU, or radio.
Data Product
Structured, file-backed science artifact created through F´ Data Products services.
Data Product writer
F´ service that serializes a typed record into the file-backed product and reports when the write is complete.
Descriptor
Small typed reference to a product: identity, byte count, source kind, Pi path, and CRC—not the pixel bytes themselves.
Selector
Routing seam that sends one manager request to the currently selected Lepton or Boson driver.
Rate group
Periodic F´ execution lane. This deployment ticks work at 1 Hz, 0.5 Hz, and 0.25 Hz.
.fdp
F´ Data Product container. The camera pixels live inside a typed record, not a normal PNG.
CRC
Cyclic Redundancy Check for corruption detection. Integrity check, not cryptographic authentication.
RFM23BP
433 MHz half-duplex packet radio used for the MVP RF link.
RadioHead
Embedded radio library used by the Teensys; its header fields carry mission/node/version identity here.
UART
Byte-oriented serial link. One physical Pi↔satellite-Teensy UART is multiplexed into logical channels.
RPC
Remote Procedure Call. Satellite UART channel 2 requests a bounded action from the satellite Teensy and returns status.
Target 3 / 4
Satellite-local channel-2 RPC endpoint IDs: target 3 owns the science cache; target 4 owns preview staging.
Local emulator / replay
Laptop-only stand-ins and checked-in data that exercise software paths without claiming Pi, radio, firmware, or camera HIL.
Triple-Serial
One ground Teensy USB device with three interfaces: interface 0 GDS, interface 1 debug, and interface 2 payload.
HIL
Hardware in the loop: proof using the real Pi UART, firmware, radios, USB, and camera.
EPS / PDU
Electrical Power System / Power Distribution Unit. Accessed behind the satellite Teensy local RPC path.
Lepton
160×120 thermal camera; science values are U16 centikelvin samples.
Boson
320×256 thermal camera; current science product preserves raw U16 sensor counts.
