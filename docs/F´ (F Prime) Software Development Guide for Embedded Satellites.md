# **F´ (F Prime) Software Development Guide for Embedded Satellites**

F Prime (F´) is an open-source flight software framework developed by NASA JPL for building reliable embedded systems (used in CubeSats, the Ingenuity Mars helicopter, etc.). It provides a component-based architecture, code generation tools, and a rich tooling ecosystem to design, build, and test flight software . This guide summarizes how to become an F´ software developer for a satellite project, focusing on using the F´ CLI tools ( fprime-util and fprime-bootstrap ) and following best practices for F´ development. It covers setting up a project on a macOS development environment, the core F´ concepts (ports, components, topologies), the development workflow (high-level design, implementation, testing), and how to build and run your F´ application with native Raspberry Pi builds for deployment. [1](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=) [2](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=Each%20Component%20defines%20a%20set,run%20when%20the%20command%20arrives)

# **Setting Up an F´ Project (Bootstrapping and Build Environment)**

To start working with F´, you should create a new F´ project and set up the build environment. F´ uses C++ and CMake under the hood, but the recommended approach is to use the provided Python tools to manage your project and dependencies in an isolated environment : [3](https://fprime.jpl.nasa.gov/latest/docs/getting-started/installing-fprime/#:~:text=The%20ecosystem%20of%20tools%20supporting,one%20virtual%20environment%20per%20project) [4](https://fprime.jpl.nasa.gov/latest/docs/getting-started/installing-fprime/#:~:text=3)

- **Install F´ Bootstrap Tool:** Ensure you have Python 3.9+ and pip available on your system . Then install the F´ bootstrap utility using pip: pip install fprime-bootstrap . This tool will create a new project and set up a Python virtual environment for F´ . *(Tip: On macOS, if you encounter SSL errors during pip install, refer to the docs for [fixing macOS SSL issues] .)* • [5](https://fprime.jpl.nasa.gov/latest/docs/getting-started/installing-fprime/#:~:text=Requirements%3A) [6](https://fprime.jpl.nasa.gov/latest/docs/getting-started/installing-fprime/#:~:text=1,tool) *[7](https://fprime.jpl.nasa.gov/latest/docs/getting-started/installing-fprime/#:~:text=Tip)*
- **Create a New F´ Project:** Run the bootstrap command to scaffold a new F´ project repository: •

fprime-bootstrap project

You will be prompted to enter a project name and a top-level namespace. For example, you might enter my-satellite for the repository name and MySatellite for the namespace . The bootstrap does the following automatically : [8](https://fprime.jpl.nasa.gov/latest/docs/getting-started/installing-fprime/#:~:text=The%20entrypoint%20to%20developing%20with,create%20a%20new%20project%2C%20run) [9](https://fprime.jpl.nasa.gov/latest/docs/getting-started/installing-fprime/#:~:text=%5B1%2F2%5D%20Project%20repository%20name%20%5Bmy,level%20namespace%20%5BMyFprimeProject%5D%3A%20MyProject)

- Clones the F´ framework (of a specific version) into a subdirectory (as a git submodule) and sets up the standard F´ project structure. •
- Creates a Python virtual environment ( fprime-venv/ ) within the project and installs all required F´ Python tools into it . • [10](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=Bootstrapping%20your%20F%C2%B4%20project%20created,tools%20to%20work%20with%20F%C2%B4) [11](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=This%20will%20show%20the%20following,files)
- Initializes a new git repository for your project with the proper directories. •
- **Activate the Virtual Environment:** After bootstrapping, navigate into your project directory and activate the Python venv to use F´ tools: •

cd my-satellite . fprime-venv/bin/activate

Always activate this environment when working on the project , so that fprime-util and other F´ CLI tools are available in your PATH. [4](https://fprime.jpl.nasa.gov/latest/docs/getting-started/installing-fprime/#:~:text=3)

- **Understand the Project Structure:** The new project will contain a directory structure following F´ conventions : • [12](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=ls)
- A top-level **<Name>/** folder (e.g. MySatellite/ ) where you will add your F´ **components**, **ports**, and **deployment** code. •
- A **lib/** directory containing the F´ framework as a submodule ( lib/fprime ) along with any external libraries. The core F´ C++ code and default components (in Svc , Drv , etc.) reside here . • [13](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=1.%20%60Hello%2F%60%3A%20top,files%20defining%20the%20build%20system)
- A top-level CMakeLists.txt and CMakePresets.json to configure the CMake build, and a settings.ini to customize build settings (toolchain, flags, etc.) . • [13](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=1.%20%60Hello%2F%60%3A%20top,files%20defining%20the%20build%20system)
- The fprime-venv/ directory with the Python environment and an initial README.md . •
- **Initial Build of the Project:** F´ uses a two-step build: first **generate** build files (running CMake), then **compile**. In the project root or a specific deployment directory, run: •

```
fprime-util generate
fprime-util build
```

The fprime-util generate step sets up the build environment (generates CMake cache and build directory) and usually only needs to be run once per deployment or after significant changes . The fprime-util build then compiles the F´ framework and your project code. On a multicore machine, you can append -j<N> to speed up builds. After a successful build, you'll have an F´ **deployment executable** ready (e.g. an App or Ref executable depending on your deployment name). [14](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=%60fprime,needs%20to%20be%20done%20once)

### **F´ Architecture Overview: Ports, Components, and Topology**

F´ employs a **component-based architecture** to organize software for embedded systems . The core building blocks are **Components**, which communicate via **Ports**, and are connected together in a **Topology** (the overall application structure). Additionally, F´ defines standardized data types for commanding and communication: **Commands**, **Events**, **Telemetry Channels**, and **Parameters**. Understanding these concepts is crucial before writing code: [1](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=)

**Components (Modules):** An F´ **Component** is a modular unit of behavior that contains its own state and logic. Each component typically corresponds to a distinct piece of system functionality (e.g. a sensor driver, a controller, a communication handler). Components *encapsulate* their functionality and interact with other components only through well-defined ports and commands . In • [1](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=) [15](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=)

practice, a component is implemented as a C++ class (with auto-generated base class code and userdefined inherited class) plus metadata definitions. Components can define:

- **Ports** they require or provide (interfaces to other components), •
- **Commands** they can handle (invoked by ground or sequences), •
- **Events** they can emit (for logging/notification), •
- **Telemetry Channels** they update (system state for downlink), and •
- **Parameters** they use (configurable persistent values). F´ components are often categorized as *active* (having their own thread for asynchronous port handling) or *passive* (called from others' contexts), but all share the same structural concept. •
- **Ports (Interfaces):** A **Port** in F´ is a typed interface allowing component-to-component communication. Ports come in pairs: an **output port** (think of it as an outbound call) on one component will connect to an **input port** (inbound handler) of the same type on another component . Port types define a function signature (zero or more arguments, and possibly a return value) that will be transferred when invoked . Key characteristics of ports include: • [16](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/03-port-comp-top/#:~:text=each%20port%20definition%20is%20of,being%20conveyed%20across%20the%20port) [17](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/03-port-comp-top/#:~:text=When%20using%20a%20port%2C%20the,input%20port%20at%20a%20time) [18](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/03-port-comp-top/#:~:text=A%20port%20supports%20passing%20arguments,when%20used%20on%20a%20Component)
- **Type matching:** Only ports of the same type can connect (e.g., a LogText output port can only connect to a LogText input port). These port types are defined in F´ or by the user and represent the data structure of the call . • [16](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/03-port-comp-top/#:~:text=each%20port%20definition%20is%20of,being%20conveyed%20across%20the%20port)
- **Directionality:** When used on a component, a port instance is marked as input or output, indicating the direction of invocation (not necessarily data flow). An **output port** is used by a component to call out, whereas an **input port** receives a call. (Multiple outputs can fan-in to one input, but one output cannot connect to multiple inputs) . • [19](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/03-port-comp-top/#:~:text=When%20using%20a%20port%2C%20the,input%20port%20at%20a%20time)
- **Synchronous vs Asynchronous:** Ports can be **synchronous**, meaning the call occurs on the caller's thread (like a direct function call), or **asynchronous**, meaning the call is queued and handled by the callee's component thread. This behavior, along with whether a port is guarded by a mutex, is defined as the port *kind* in the component's design . For example, an *async input* port enqueues messages to be processed later, whereas a *sync input* is handled immediately in the caller's context. Guarded ports ensure only one invocation at a time (useful for thread safety) . • [20](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/03-port-comp-top/#:~:text=Another%20aspect%20of%20port%20usage,when%20used%20by%20the%20Component) [21](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/03-port-comp-top/#:~:text=sync_input%20in%20synchronous%20no%20yes,by%20definition%20must%20be%20synchronous) [21](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/03-port-comp-top/#:~:text=sync_input%20in%20synchronous%20no%20yes,by%20definition%20must%20be%20synchronous) [22](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/03-port-comp-top/#:~:text=Figure%202,thread%20that%20empties%20the%20queue)
- **Serialization:** F´ supports automatically serializing port calls (arguments) into a generic byte buffer for transport, which allows for certain flexible connections (like connecting a strongly-typed port to a generic serial port handler) . Most of the time, you will use the typed ports directly; serialization is handled behind the scenes when crossing components like the ground interface. • [23](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/03-port-comp-top/#:~:text=Port%20Call%20Serialization) [24](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/03-port-comp-top/#:~:text=Serialization%20ports%20are%20special%20ports,be%20passed%20around%20by%20generic)
- **Topology (Deployment Composition):** A **Topology** is the assembly of component instances and connections that form a **deployment**, i.e., the final running application . The topology defines which components are included and how their ports are wired together. In F´, the topology is typically specified in two parts: • [15](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=) [25](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=)
- A topology FPP (F´ Prime Python) or XML file that lists the components and the port connections (logical design), and •
- A C++ Topology.cpp that instantiates the component objects, connects them (via autogenerated connect calls), and initializes the system (e.g., starting tasks for active components, registering command handlers, setting up ping/health, etc.) . • [26](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=1.%20In%20the%20topology%20%60,function) [27](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=2.%20In%20the%20topology%20,when%20exiting)
- A deployment equals one executable containing one topology. You can have multiple deployments

(for example, a satellite may have one flight software deployment, and maybe a separate test or simulation deployment). In this guide, we assume one primary deployment for your satellite application (often called something like Ref or SatelliteApp ). Once the topology is built and the code compiled, running the deployment will start all the component threads and enable communication as defined.

- **Commands:** A **Command** is an operation that the system can perform on request. Commands are typically sent from the Ground Data System (or from onboard sequencers) to trigger actions in components . For each component that defines commands, the F´ code generator creates the infrastructure to handle them (including dispatching ports and a handler function hook). Each command has: an **opcode** (unique ID), a **mnemonic** (unique name), a list of **arguments** (typed parameters sent with the command), and an execution context (*sync/async/guarded* like ports) which determines how the command handler runs . For example, a REBOOT command might have no arguments and be handled immediately (synchronously), whereas a SET\_PARAM command might be handled on the component's thread (asynchronous). Commands are routed through the CmdDispatcher component in F´: when a command is received (from ground or a sequence), CmdDispatcher looks up which component should handle it and invokes the appropriate port on that component . In your component code, you'll implement command handler methods for each defined command. • [2](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=Each%20Component%20defines%20a%20set,run%20when%20the%20command%20arrives) [28](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=1,commands%20execute%20on%20the%20component) [29](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=user%20interaction%20with%20a%20component,run%20when%20the%20command%20arrives) [30](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=When%20commands%20are%20defined%20for,and%20response%20ports%20in%20parallel)
- **Events:** An **Event** is a log message or notification generated by a component to record that something happened (especially for status or error reporting) . Events have a **severity level** (e.g. DEBUG/DIAGNOSTIC, WARNING\_HI, FATAL, etc.), a unique **ID and name**, optional **arguments** (data associated with the event), and a **format string** used to construct human-readable text . When a component emits an event (by calling the generated event function), the framework tags it with a timestamp and routes it to the event logging system ( EventManager component). Typically, events are forwarded to ground (and also to a local console logger for debugging) . Events allow operators and developers to trace what the software is doing in real-time or post-fact via logs. • [31](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=Events%20represent%20a%20log%20of,defined%20by%20the%20following%20properties) [32](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=1,these%20typically%20come%20from%20foreground) [33](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=4,to%20reconstruct%20a%20text%20version) [31](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=Events%20represent%20a%20log%20of,defined%20by%20the%20following%20properties) [34](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=Code%20in%20the%20component,independent%20ports%20for%20sending%20events)
- **Telemetry Channels:** A **Channel** (telemetry channel) represents a piece of numeric or state data that the software periodically reports to the ground . Each channel has an ID, name, and a data type (and possibly an update scheme like *on-change* or *always*). For example, you might have a channel for battery voltage or for the count of messages processed . The component's generated code provides a way to update the channel value in the software, which then gets sent out (typically via a TlmChan component that aggregates and downlinks telemetry). Channels are key for monitoring the health and status of the satellite over time. • [35](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=Channels) [36](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=1,and%20omitted%20to%20always%20downlink)
- **Parameters:** A **Parameter** is a configuration value or persistent state that can be changed and saved. Parameters are often used for things like tunable constants, mode settings, or thresholds that you might want to adjust without recompiling code . Each parameter has an ID, name, type, and a default value . F´ provides a parameter management component ( PrmDb ) that stores parameters in non-volatile storage (e.g., a file) so they persist across reboots . The framework auto-generates setter/getter ports for parameters, and even auto-generates commands to **set** a parameter value and **save** it (commit to storage) at runtime . This way, an operator on the ground can send a command to update a parameter and save it, which is very useful for configuration tweaks on orbit. • [37](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=Parameters%20are%20traditional%20means%20of,defined%20by%20the%20following%20properties) [38](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=The%20framework%20provides%20the%20ability,file%20to%20persist%20across%20reboots) [39](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=component,the%20following%20properties) [38](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=The%20framework%20provides%20the%20ability,file%20to%20persist%20across%20reboots) [40](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=Image%3A%20Parameter%20Database)

**Reuse of Framework Components:** F´ comes with a library of standard components (often under the Svc and Drv namespaces) that implement common functions: e.g., command dispatching, event logging, telemetry collection ( TlmChan ), time keeping ( Time ), ping/health monitoring ( Health ), file downlink ( FileDownlink ), etc. Part of the design process is deciding which of these you will use as-is. The F´ user manual suggests leveraging existing framework components whenever possible to avoid reinventing the wheel . For a satellite project, you will almost certainly include the basic *command and data handling (C&DH)* components provided by F´ (command dispatcher, telemetry channel aggregator, event logger, parameter database, etc.), plus any device drivers or protocol components needed. These built-in components can be integrated into your topology alongside your custom mission-specific components. [41](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=Next%2C%20the%20project%20should%20review,fall%20short%20of%20project%20requirements)

### **Development Workflow and Best Practices**

Developing an F´ project typically follows a structured process . Below is a high-level outline of the recommended workflow, from initial design to running on target hardware, with emphasis on how to use the F´ tooling (CLI commands) at each step: [42](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=The%20first%20step%20of%20the,See%3A%20Ports%20Components%20and%20Topologies) [43](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=Integration%20Testing)

### **1. High-Level Design and Planning**

Begin by defining the **system-level requirements** and breaking down the major functions of your satellite software . From this, derive a *block diagram* or architecture diagram of components and their interactions (this can be done on paper or a whiteboard initially). In this stage: [42](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=The%20first%20step%20of%20the,See%3A%20Ports%20Components%20and%20Topologies)

- **Identify Components and Interfaces:** Decide what components you need to implement to meet the requirements. For example, you might have components for **ADCS** (attitude determination and control), **ThermalControl**, **Communication (Radio)**, **Power Management**, etc., depending on your satellite's subsystems. Also identify interactions: e.g., the ADCS component might need to send telemetry or events, or receive commands and sensor data via ports. Each interaction becomes an **interface (port)** in F´ terms. Define these **ports** and what data they carry (e.g., a port to send a thruster fire command might carry a duration or force value). At this stage, you are essentially designing the *F´ topology* on paper: what components and what connections (ports) between them . • [44](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=represent%20the%20system,See%3A%20Ports%20Components%20and%20Topologies) [45](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=further%20broken%20down%20into%20discrete,See%3A%20Ports%20Components%20and%20Topologies)
- **Leverage Existing Components:** Cross-check your needed functionality against F´'s provided components. Many common needs (time sync, commanding, telemetry, file transfer, parameters, watchdog timers, etc.) are satisfied by the built-in Svc components. Use them where appropriate rather than writing your own from scratch . For instance, if you need to log events or store parameters, plan to use EventManager and PrmDb instead of custom solutions. This inheritance of functionality "for free" will save time and improve reliability . Document which components will be reused and which ones you must implement custom. • [41](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=Next%2C%20the%20project%20should%20review,fall%20short%20of%20project%20requirements) [41](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=Next%2C%20the%20project%20should%20review,fall%20short%20of%20project%20requirements)
- **Assign Component Responsibilities:** Now you have a list of custom components to implement. For each, write a short description of its responsibility and list the **commands** it should handle (if any), **events** it should emit, **telemetry channels** it should produce, and any **parameters** it needs. Also list which **ports** it requires/provides and with which other component those will connect. This essentially forms the specification for each component (you can consider these the component-level requirements). •

This high-level design phase is crucial. By its end, you should have a clear idea of the *components*, *ports*, and overall *topology* of your flight software . This will guide the subsequent implementation steps. [44](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=represent%20the%20system,See%3A%20Ports%20Components%20and%20Topologies) [46](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=further%20broken%20down%20into%20discrete,See%3A%20Ports%20Components%20and%20Topologies)

#### **2. Setting Up the Deployment**

With the design in mind, the next step is to implement a minimal working *deployment* (application) that includes the basic skeleton of your topology. There are two approaches to structuring your project repository for the deployment:

- **Standalone Project (Out-of-Tree Deployment):** This is the approach we initiated with fprimebootstrap . Your project lives outside the F´ core, with F´ included as a submodule (e.g., under lib/fprime ). This keeps your code separate from the framework code, which is beneficial for updating F´ later and for clarity . In this approach, you will create a new deployment in your MySatellite/ folder (if not already created by bootstrap) and point it to use the F´ submodule. The bootstrap might already provide an example or empty *Ref* deployment you can copy. (F´ often includes a Ref application as a reference design – copying and renaming it is a quick way to start a new deployment.) • [47](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=You%20can%20create%20an%20in,used%20as%20a%20starting%20point) [48](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=mission%20%E2%94%9C%E2%94%80%E2%94%80%20mission_deployment_1%20%E2%94%9C%E2%94%80%E2%94%80%20fprime,submodule%20to%20an%20external%20library)
- **In-Tree Deployment (within F´ source tree):** Alternatively, one could place their project inside the F´ repository itself (for example, adding your deployment under fprime/Ref or similar). This is generally **not recommended for long-term projects**, as it mixes your code with F´ code, making upgrades difficult . If you go this route, the user guide suggests copying the Ref application that comes with F´ and modifying it . But since we used fprime-bootstrap , you likely already have a standalone structure. • [49](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=There%20are%20two%20options%20for,creating%20a%20deployment) [49](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=There%20are%20two%20options%20for,creating%20a%20deployment)

Given we have a standalone project, do the following to set up your **deployment** (the top-level application):

- **Create a Deployment Folder:** In the MySatellite directory (the namespace directory created by bootstrap), you might already have an initial deployment (for example, MySatelliteDeployment ). If not, you can create one manually or via fprime-util . For instance, you could create MySatelliteDeployment directory with a CMakeLists and topology, or run a command like fprime-util new --deployment . (If using fprime-bootstrap project , often it sets up a default deployment for you named after your namespace.) Ensure your project's CMakeLists.txt (or settings.ini ) registers this deployment. The typical CMake pattern is to use add\_fprime\_subdirectory(MySatelliteDeployment) in your top-level CMake so that the deployment is included in the build . • [50](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=After%20copying%20the%20Ref%20app%2C,location%20of%20the%20F%C2%B4%20framework)
- **Configure settings.ini :** Each deployment or project has a **settings.ini** file to configure build options. At this stage, update settings.ini with any necessary settings: specify the F´ framework path (for standalone deployments, the framework\_path should point to your lib/fprime directory) and other options (like component\_cookiecutter templates, if customizing code generation). The default settings.ini from bootstrap may already have reasonable defaults. • [50](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=After%20copying%20the%20Ref%20app%2C,location%20of%20the%20F%C2%B4%20framework)

At this point, you should have the basic project ready to add your components. You can do a test build of the empty deployment to ensure everything is wired correctly (even if it just builds the included F´ library components). Use: fprime-util generate && fprime-util build in the deployment directory to verify the build succeeds. If you copied an example (Ref) topology, you might already have some components wired (like command dispatcher, etc.) – that's fine as a starting point.

#### **3. Developing Ports and Components**

With the deployment structure in place, developers can start creating the custom ports and components identified in the design. F´ provides automation to create boilerplate code and definitions through fprime-util commands, or you can do it manually. The general sequence is: **define needed ports first**, then **define components**, then implement them.

**Design Note:** Typically, you create **custom Port types** only if the built-in ports do not cover your needs. F´ comes with many pre-defined port types (e.g., for commands, telemetry, logging, time, etc.). But for custom interactions (like a port to send a complex sensor reading from one component to another), you might define a new port type.

- **Creating a Custom Port Interface:** If your design calls for a new port type (i.e. a custom interface), you can add it. It's recommended to keep port definition files in a separate directory (e.g., MySatellite/Ports/ ) distinct from components . You can create a port definition by writing an F´ port definition file ( .fpp file describing the port's name, data types, and arguments). The typical steps (if doing manually) are : • [51](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=Once%20the%20interfaces%20between%20components,port) [52](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=It%27s%20recommended%20that%20ports%20are,own%20directories%2C%20separate%20from%20components) [53](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=To%20create%20a%20new%20port%3A)
- Make a new directory for your port (e.g., MySatellite/Ports/MySensorPort/ ). •
- Create a MySensorPort.fpp file defining the port (with a unique namespace and the port's input/ output signature). •
- Update the CMakeLists.txt in the Ports directory to include this .fpp in SOURCE\_FILES . If a CMakeLists doesn't exist, create one. • [54](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=1,add_fprime_subdirectory)
- If the Ports directory itself wasn't included yet, add add\_fprime\_subdirectory(Ports) in your deployment CMake. •

**Using fprime-util to create a port:** A faster method is to run:

```
fprime-util new --port
```

This will prompt for the port name, namespace, and directory, and then automatically: (a) create the directory if needed, (b) generate the .fpp file with the specified arguments, and (c) update or create the CMakeLists.txt with the new port source . This is highly convenient. For example, if you need a port SensorReadings with an argument of a struct, the tool will ask for those details and fill them in. After generating, you can open the .fpp to double-check or edit the specifics. [55](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=Alternatively%2C%20you%20may%20use%20%60fprime,following%20will%20be%20done%20automatically) [56](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=1,add_fprime_subdirectory)

**Creating a Component Definition:** Once ports (interfaces) are in place, proceed to create each custom **Component** as designed. Each component is defined primarily by an F´ **component specification file** (also .fpp extension in newer F´ versions, which replaces the older .ai or .xml formats). In this file you declare the component's name, the namespace, the kind of component (active/passive), the input/output ports it uses (referring to port types, and giving them •

names), the commands, events, channels, and parameters it contains. To create a new component, you can also choose between manual or tool-assisted methods:

- *Manual Component Creation:* Make a directory for the component (e.g., MySatellite/Components/ MySensor/ ). Inside it, create MySensor.fpp describing the component (you can copy an example from the F´ repo or tutorials as a starting point). Optionally, for clarity, you can separate command, event, and channel definitions into included files ( .fppi include files) , but this is not required. Write a CMakeLists for the component listing the .fpp file in SOURCE\_FILES and then include this component directory in the deployment's CMake with add\_fprime\_subdirectory(MySensor) . This manual approach gives fine control but is more labor-intensive. • [57](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=2,add%20the%20component%20file%20to) [58](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=5,add_fprime_subdirectory)
- *Using fprime-util to create a component:* The easier way is to run: •

```
fprime-util new --component
```

This interactive CLI will ask for details such as component name, namespace, base ID (used for opcodes/channel IDs offset), whether it's active or passive, and whether you want to include command/telemetry/event/param support. It then generates the component's directory and populates: the .fpp definition (with the chosen ports and data constructs stubbed out), a CMakeLists.txt for the component (already adding it to build), and even an SDD (software design document) markdown file with component details . You'll also be prompted if you want to auto-generate the C++ implementation files and a unit test suite for this component . If you say "yes", it will run the equivalent of impl and create MySensorComponent.hpp/cpp with skeleton code, and set up a test/ folder with unit test stubs. This **cookiecutter** template greatly accelerates initial setup . (Note: the template generation can be customized via settings.ini if needed , but default is usually fine.) [59](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=Alternatively%2C%20you%20may%20use%20%60fprime,following%20will%20be%20done%20automatically) [60](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=5.%20A%20component%20,documentation%20about%20ports%2C%20commands%2C%20events) [61](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=Component%20Implementation) [62](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=If%20%60fprime,because%20these%20are%20automatically%20done) [63](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=1,the%20user%20chooses%20to%20include) [64](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=should%20explicitly%20state%20in%20the,for%20their%20ports) [65](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=The%20%60fprime,more%2C%20see%20the%20Cookiecutter%20Documentation)

Using fprime-util new --component is recommended for new projects to ensure everything is wired correctly. For instance, if you indicated your component will have commands, the tool will automatically add the required **Cmd** ports to the component and include a placeholder command in the .fpp . Similarly, if you include telemetry or parameters, it adds the Tlm and Prm ports as needed. This saves you from forgetting critical pieces. [63](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=1,the%20user%20chooses%20to%20include)

**Implementing the Component (C++ code):** After defining a component in FPP, F´'s **autocoder** will generate a base C++ class for it when you build the project. However, you still need to implement the custom logic in a derived class. If you used the --component generator and opted to create implementation files, you will already have <Component>ComponentImpl.cpp and .hpp with stub methods. If not, you can generate them by running: •

```
fprime-util impl <ComponentName>
```

in the component's directory. This will create ComponentNameComponentImpl.hpp/cpp with each port handler, command handler, etc., as empty stub functions that you can fill in . (Without using impl , you would have to manually write these files, but following the exact naming and class [61](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=Component%20Implementation)

inheritance structure that F´ expects.) Once you have the template, open the .cpp and implement the logic for each of your component's handlers. For example, if you have a command CALIBRATE defined, implement the handle\_Cmd\_CALIBRATE() function to perform the calibration and then emit any events or telemetry as needed. Likewise, implement any incoming port handler functions (e.g., if your sensor component has an input port for new sensor data, code what to do when data arrives).

As you implement, you can leverage the auto-generated helper methods: e.g., for events and channels, the base class provides log\_ACTIVITY\_HI\_EventName(arg1, arg2, ...) to log an event , or tlmWrite\_ChannelName(value) to set a telemetry channel value, and paramGet/paramSet for parameters. These functions hide the lower-level port calls and should be used to ensure the data goes through the framework properly. [34](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/04-cmd-evt-chn-prm/#:~:text=Code%20in%20the%20component,independent%20ports%20for%20sending%20events)

**Build Frequently:** As you add new ports and components, run fprime-util build regularly to catch errors early. The first time after adding new FPP files, you may need to run fprime-util generate again so CMake picks them up (the fprime-util new commands often update CMake for you, but if you added things by hand, regenerate). The build will run the autocoder to generate C++ from your FPP definitions and then compile everything. Fix any compilation errors as you go. By the end of this step, you should have all your custom components defined and implemented at least in a preliminary way. •

### **4. Unit Testing Components (Optional but Recommended)**

F´ strongly encourages writing **unit tests** for each component's logic. This ensures reliability for flight software. If you enabled unit test generation when creating the component (or run fprime-util impl --ut later) , you will have a test directory with a skeleton Google Test (gtest) based suite. The typical steps to set up tests are : [66](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=1,directory%20to%20run%20unit%20tests) [67](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=1,directory%20to%20run%20unit%20tests)

- Ensure there is a <Component>/test directory with a CMakeLists.txt that includes UT\_SOURCE\_FILES . The fprime-util impl --ut command should have created this along with a test cpp file. It also should register the test binary with CMake. •
- In the component's CMakeLists, verify that register\_fprime\_ut() is called to register the unit test target . The cookiecutter likely did this for you. • [67](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=1,directory%20to%20run%20unit%20tests)
- Write your test cases in the generated test file. Typically, you create a test fixture that instantiates your component and perhaps some test stubs or uses the GDS integration test API for simulating port inputs. •
- To build and run tests, use the --ut flag with fprime-util . For example: •

```
fprime-util generate --ut
fprime-util build --ut
fprime-util check --ut
```

The --ut option tells F´ to include unit test targets. fprime-util check will execute the unit tests and report results . Make sure all tests pass. (If you encounter linking issues, ensure you have required gtest libraries, but F´ usually bundles it or fetches it via CMake.) [68](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=2.%20Run%20%60fprime,directory%20to%20run%20unit%20tests)

Writing tests for each component as you implement will catch bugs early and also serves as documentation of expected behavior. While this might be extensive for an initial MVP, it's a good practice for flight software.

#### **5. Assembling the Topology**

As individual components are developed, you will integrate them into the overall **topology** (the deployment). This is where you "wire up" the system. By now you should have a topology definition (from the design stage) that you can translate into F´ code:

- **Topology FPP File:** Define a topology file (e.g., MySatelliteTopology.fpp ) where you declare instances of each component and the connections between ports. For example, if you have a Comm component and a Radio component, you might instantiate them as comm = Comm() and radio = Radio() , then connect comm.uplinkOut -> radio.uplinkIn (using the FPP port connection syntax). The FPP topology describes the network of components at a high level (it's like a wiring diagram in code form) . F´ will autogenerate corresponding C++ hookup code for connections. • [69](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=To%20add%20a%20component%20to,the%20topology)
- **Topology C++ Implementation:** The FPP topology is compiled into a C++ class (often named something like MySatelliteTopologyApp ) with static connect functions. You also maintain a Topology.cpp (and possibly Topology.hpp ) manually where you: •
- Instantiate each component object (matching the instances declared in FPP) . • [70](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=2.%20In%20the%20topology%20,function)
- Call the auto-generated connect() function to connect all the ports as specified. •
- Perform any additional initialization: e.g., allocate message buffers if needed, call component.init(...) on each (to initialize base classes with instance IDs), register component commands with the CmdDispatcher (typically done via a provided macro or function for each component that has commands) , add components to the health checker ping list if using the Health component (so it knows what to ping), and start the tasks for active components by calling component.start() for each active component thread . Also, set up run-time wiring such as event reporting: often the EventManager and TlmChan are wired to ground interfaces here. Many reference topologies (e.g., Ref app) illustrate these steps, so consider using one as a template. • [71](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=,when%20exiting) [71](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=,when%20exiting)
- **Include Framework Components:** In Topology assembly, don't forget to include the standard F´ service components in the topology and connect them. For instance, instantiate CmdDispatcher , CmdSequencer (if using command sequencing from files), EventManager , TlmChan , PrmDb , FileUplink/FileDownlink (if doing file transfer), and any driver components (like TcpServer or SerialDriver for comms) as needed. Wire all their ports accordingly. For example, connect all components' CmdReg ports to the dispatcher's registration port, all commands out of sequencer or ground to the dispatcher's input, events to event manager, etc. The F´ user manual's diagrams (and the reference topology) are very useful to get this right. Essentially, by the end, *every required port of every component should be connected* either to another component's port or left unconnected on purpose (some optional outputs can be left unconnected if not needed). •

**Build the Full System:** Once topology code is written, do a full build: fprime-util generate && fprime-util build at the deployment level. This will compile all components and the final executable for your deployment. If all goes well, you now have a complete **satellite software application** compiled for your host (macOS for simulation). •

#### **6. Testing on Desktop (Simulation)**

Before deploying to actual hardware, test the system on your development machine (desktop simulation). F´ provides the **Ground Data System (GDS)** tools to run and interact with the software. There are two interfaces: a command-line interface and a web-based dashboard. The easiest is to use the web dashboard via the fprime-gds command:

**Running the Deployment with GDS:** In your deployment directory (where the ArduinoExecutable or similar binary was built, typically under build-artifacts or build/ ), launch the ground system: •

fprime-gds

This will start the F´ deployment executable and open a web UI for the GDS . By default, the GDS will attempt to launch the binary for the deployment you built (it looks for the deployment executable as configured by CMake). If the web UI (at http://127.0.0.1:5000) opens and shows a green connection status, it means the flight software is running and connected to the GDS . If you see a red X (disconnected), check the logs in the UI; you may need to configure the GDS to point to the correct binary or ensure the binary finds the correct port (usually localhost socket) – but by default fprime-gds should handle local deployments. [72](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=To%20start%20the%20deployment%20with,default%20settings%2C%20run) [73](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=The%20F%C2%B4%20GDS%20control%20page,http%3A%2F%2F127.0.0.1%3A5000) [74](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=Once%20the%20F%C2%B4%20GDS%20page,errors%20in%20the%20various%20logs)

- **Using the GDS Dashboard:** Through the web interface, you can perform integration testing of your software: •
- Go to the **Commanding** tab and send commands to your components. You should see your custom commands listed under the component instance names (for example, MySatellite.ADCS.COMPONENT\_NAME.CMD\_NAME style) . Send a few test commands (e.g., a *hello* command or mode changes) and ensure you get the expected response. • [75](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=Now%20that%20communication%20is%20verified%2C,ensure%20the%20command%20has%20sent)
- Check the **Events** tab to see if your components are logging events as expected (e.g., a "calibration complete" event shows up after sending a CALIBRATE command) . • [76](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=component%20instance) [77](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=Now%20that%20the%20command%20has,entered%20when%20sending%20the%20command)
- Check the **Channels** tab to monitor telemetry values updating (e.g., your GreetingCount or sensor readings) . • [77](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=Now%20that%20the%20command%20has,entered%20when%20sending%20the%20command)
- Ensure the **Parameter** tab (if available) shows your parameters and you can update them (via sending parameter update commands or using the GUI if supported). •

This manual testing validates that the system is wired correctly. The GDS is also useful for debugging: if something is not working, use the Event log or the console output to see errors (like unconnected ports or asserts).

**Automated Integration Testing:** For more rigorous testing, F´ has a Python API to automate the GDS interactions (sending commands, verifying events/telemetry) . You can write integration test • [43](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=Integration%20Testing)

scripts that bring the system up, send a series of commands, and check that the resulting telemetry/ events match expectations. This is especially useful for regression testing as the project grows, but might be more advanced usage.

At this stage, on your Mac development machine, you essentially have a fully functional satellite software **simulation** running. This is useful to iron out logic bugs before moving to real hardware.

#### **7. Native Build and Deploy on Raspberry Pi (Linux Target)**

For the MVP, run the software on Raspberry Pi by building directly on the Pi.

- SSH into the Pi
- set up Python venv + project requirements
- run `fprime-util generate -f`
- run `fprime-util build`
- run deployment on `/dev/null` first, then `/dev/serial0`

Use the repo runbook for exact commands:
- `rpi_build.instructions`

By following this path, the generated binary matches the target CPU and avoids architecture-mismatch runtime failures.

### **F´ CLI Tools Quick Reference**

Throughout the development process, you primarily interact with F´ via command-line tools. Here's a summary of key tools and commands (all run within your project's virtual environment):

- **fprime-bootstrap :** Used once to create a new project. Example: fprime-bootstrap project (prompts for name/namespace) creates a new F´ project repo with a virtual environment and F´ framework cloned . • [8](https://fprime.jpl.nasa.gov/latest/docs/getting-started/installing-fprime/#:~:text=The%20entrypoint%20to%20developing%20with,create%20a%20new%20project%2C%20run)
- **fprime-util :** Main CLI for building and code generation. Key usages: •
- fprime-util new --component : Scaffold a new component (creates .fpp, C++ files, CMake, etc.) . There are also --port (new port) , --deployment (new deployment), and - cookiecutter options. • [59](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=Alternatively%2C%20you%20may%20use%20%60fprime,following%20will%20be%20done%20automatically) [55](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=Alternatively%2C%20you%20may%20use%20%60fprime,following%20will%20be%20done%20automatically)

- fprime-util impl [--ut] : Generate implementation files for a component. With --ut , also generate unit test files . (If new --component was used and you opted to generate impl, you may not need this.) • [61](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=Component%20Implementation) [66](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=1,directory%20to%20run%20unit%20tests)
- fprime-util generate [<platform>] : Run CMake to configure the build. Commonly used as `fprime-util generate -f` for native builds. Use --ut to include unit test targets in generation. • [14](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=%60fprime,needs%20to%20be%20done%20once)
- fprime-util build [<platform>] : Compile the code. Add -j for parallel jobs. Use same platform as generated. Append --ut to build unit tests. For Raspberry Pi deployment in this project, run native build on the Pi. •
- fprime-util check [--ut] : Runs tests (unit tests if --ut specified) to verify the build . • [67](https://fprime.jpl.nasa.gov/latest/docs/user-manual/overview/development-practice/#:~:text=1,directory%20to%20run%20unit%20tests)
- There are other subcommands like fprime-util purge (clean build artifacts), fprime-util info (show project info), etc., and you can run fprime-util --help for a full list . • [85](https://fprime.jpl.nasa.gov/latest/tutorials-hello-world/docs/hello-world/#:~:text=Troubleshooting)
- **fprime-gds :** Launches the Ground Data System web interface and, by default, runs the F´ deployment. When run in a deployment directory, it uses configuration in deployment/settings to know which binary to execute and how to connect. You can also use fprime-gds-cli for a console-based interaction or automated scripts (but the web UI is easier for manual use). •
- **Platform-specific tools:** If working directly on Linux, you might use make or CMake directly, but it's generally easier to use fprime-util . On the Raspberry Pi (if you choose to compile there natively), you would still use fprime-util (since it's installed in the venv for your project) but you might just do fprime-util build which will use the Pi's native GCC. •
